# Execution and Effects

Choose execution from the accepted visual postcondition and evidence obligations,
not from the most visible installed tool. The portable capability owns the visual
decision. The current project owns its environment and source. A selected adapter
owns execution effects and returns observable evidence; availability is neither
compatibility nor authorization.

## Map the result to required capability

Name the accepted result, then select its capability below. These are independent
operations, not maturity levels. Use [quality evaluation](quality-evaluation.md)
**Match evidence to the claim** for the quality evidence each operation must make
observable; this reference owns tool admission, effects and recovery.

| Accepted result | Required capability |
| --- | --- |
| Representation decision or executable intent | Inspect authoritative inputs; express encoding, structure, quality criteria and unresolved obligations. |
| Editable source | Author and parse/inspect the selected native or textual representation. |
| Rendered static artifact | Render the exact revision with the delivery engine or a bounded declared substitute; inspect at target dimensions/scale. |
| Temporal or encoded media | Deterministically evaluate time/state, render/capture, and encode/probe the requested carrier, including timing/dimensions/rate/audio when applicable. |
| Interactive visualization | Run the actual model and exercise relevant input/state paths, including keyboard/non-visual access and fallbacks. |
| Native container result | Use the container owner's admitted producer/editor/renderer to preserve native structure; supply representation/perceptual review within this skill's scope. |
| External generation, data or rendering | Use an authorized bounded provider adapter; bind request/target/revision and validate returned content as untrusted under the external-operation contract below. |

Do not weaken the quality contract to fit available tools. When a capability is
missing, keep purpose, source truth and quality obligations stable while changing
the operation, output and completion claim honestly.

## Select the smallest compatible operation

Inspect the task root, applicable instructions, current source/output, manifests,
locks, configured manager, environment directories and relevant available tools.
Then prefer:

1. the current project's compatible native authoring and observation path;
2. a compatible capability already provided by the user or host;
3. a direct native/textual operation with an observable result;
4. a minimal project-local dependency through the project's manager; or
5. an explicitly selected external provider when its benefits and effects fit.

This order is a preference, not a command to use an inferior existing tool. The
operation must preserve accepted content, editability, carrier requirements and
evidence. Do not migrate a project merely to use a favored framework. Read-only
review, source-only work or a direct operation needs no new scaffold.

For new durable work, place source, manifests, locks, dependencies and outputs in
a named task project beside their intended consumer. Use an owned disposable area
for temporary render/capture work. Never write task outputs into the installed
skill directory. For required setup, optionally use the host owner's
[project environments](../../system-mutation/references/project-environments.md).
If absent, preserve the selected manager, constraints and storage settings; acquire
only the authorized missing capability or report its unavailability. Visual
decisions do not require that sibling skill.

Acquire only a proven missing requirement under existing authority. Avoid global
installs, profile or `PATH` changes, hidden downloaders, environment registries and
custom setup wrappers for routine use. A package launcher, manager shim, browser,
font, model or renderer can download on first use; inspect and admit that network,
storage and version effect. Project-local dependencies reduce conflicts but do not
sandbox untrusted code or all operating-system writes.

## Admit each operation

Before executing, resolve the fields that affect this selected edge:

- exact source/input and output identities, overwrite/preservation policy and
  current revision;
- required capability, selected tool/provider/version and known compatibility;
- files, processes, network, code execution, downloads and external data effects;
- dimensions, scale, time/state, fonts/assets, color/media and target carrier;
- bounds on size, duration, frames, memory, concurrency, timeouts and attempts;
- cancellation, partial-output, retry/idempotency, cleanup and recovery behavior;
  and
- the quality reference's selected evidence obligations and operational
  post-observation needed after execution.

Select authoring, rendering, interaction, capture, encoding and inspection
independently. A caption edit does not require reinstalling a renderer; an MP4
request does not choose a language or make the encoder the source owner.

Execute trusted project code only within its admitted authority. Treat parsed
files, remote responses, generated media, archives, redirects and provider
metadata as untrusted at their boundary. Validate them before execution,
extraction, rendering, incorporation or publication.

## Use frameworks, templates and assets as priors

A framework can supply a deterministic runtime, layout primitives, state model or
fast feedback. A template can supply a tested hierarchy. Assets can supply visual
language and production detail. Select them when those capabilities reduce risk or
iteration cost for this contract.

Before use, inspect fit, editable representation, dependency closure, project
compatibility, version, license/provenance, content assumptions, visual bias,
supported states and validation route. Copy or adapt resources into the task
project only when their license and role permit. Preserve project edits and record
material adaptation. Do not let a strong example become factual evidence,
mandatory aesthetics or proof of an unrelated carrier.

If the prior constrains the intended meaning, accessibility, native structure or
quality more than it helps, choose or construct another route. Feature parity is
not required; preservation of the accepted contract is.

## Bound external visual operations

Before data, source, prompts or media leave the project, identify:

- why the remote capability is needed and what is disclosed;
- the authorizing user, account, provider, endpoint and destination;
- credential owner and least required scope, without exposing secrets in source,
  commands, assets or logs;
- sensitivity, retention, training/reuse, deletion, license, attribution and
  provenance obligations;
- model/API/tool version, output identity and reproducibility limits;
- price/quota, size, concurrency, timeout, cancellation and maximum attempts;
- whether the operation is read-only, billable, mutating or publishing, including
  idempotency and uncertain-commit handling; and
- local validation, fallback, recovery, cleanup and residue reporting.

Connected does not mean authorized. Generation authority does not imply
publication authority. Do not retry a possibly committed billable or publishing
operation without idempotency or observation that prevents duplication. Inspect
remote output before treating it as a usable asset. Generated imagery may support
explanation or atmosphere but never becomes evidence for data or factual claims.

For external map tiles/data, preserve attribution, geographic/source semantics,
freshness, licensing and offline implications. For hosted rendering, verify the
returned artifact and current source identity locally. For remote data connectors,
keep read authority separate from permission to persist, transform or publish.

## Degrade and recover honestly

When the selected capability is unavailable:

- choose a compatible alternative only if it preserves the accepted contract;
- return editable source or an executable specification and name the required
  render/runtime/encode checks still missing;
- return a bounded partial artifact with missing states or guarantees explicit;
- request genuinely missing authority or a material user decision; or
- report precise unavailability.

Keep unavailable capability, missing authority, missing credentials, rejected
input, setup failure, timeout, cancellation, partial output, invalid output,
uncertain remote commit, verification failure and cleanup failure distinct.

After interruption, inspect actual local and remote state before retrying. Preserve
useful partial output and evidence when safe. Clean only owned disposable work
whose identity remains certain; close owned processes. Report irreversible data
disclosure, charges, remote mutations, retention and uncertain commits plainly.
Release disposable capture/render environments once their evidence is complete;
retain maintained project environments. Shared-cache maintenance is a separate
host operation.

Return the exact source/output, selected operation, observed evidence, effects and
remaining limitations. Successful execution supports only the claims it actually
made observable.
