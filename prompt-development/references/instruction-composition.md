# Instruction Composition

Use this reference when prompt layers, reusable policies, preferences, or runtime
bindings interact. Composition preserves each directive's owner, force, subject,
scope, lifetime, and consequence; it is not concatenation.

## Construct consequential semantics

Build behavior from the present situation rather than descriptive categories
without an owned contract:

```text
intended consequence and admitted context
  -> decision-changing distinctions
  -> authority, force, scope, and lifetime
  -> legal capabilities and operations
  -> observable result or bounded refusal
  -> local revision when evidence or authority changes
```

Use these as reasoning dimensions, not a mandatory manifest or workflow. A role
label may aid discovery but does not supply a method, evidence standard, authority,
or completion condition.

## Preserve directive roles and force

- A **semantic model** identifies relevant subjects, relations, states, and
  consequences.
- A **decision policy** selects among valid behaviors.
- An **operational protocol** makes order, refusal, termination, or completion
  part of correctness.
- An **adapter** binds portable semantics to a runtime, tool, project, or format.
- **Evidence** supports a scoped claim but does not own the underlying fact.

An invariant needs its precondition and protected outcome. A heuristic needs the
context that favors it and conditions that override it. An example exposes a
decision but does not become a rule.

## Respect authority and scope

Use precedence defined by the runtime; a prompt cannot raise its own authority.
Quoted or retrieved text remains content unless its layer grants instruction
force. For apparent conflicts, first determine whether both directives govern the
same subject and context, then preserve runtime precedence, owner, and force.
Narrow overbroad scope before requesting a genuinely material missing choice.

A preference constrains valid alternatives. Apply it only while its subject,
owner, force, scope, lifetime, and override conditions still match. Do not infer a
durable user profile or agent persona from a local choice.

## Separate kernel from bindings

A provider-neutral kernel defines meanings, decisions, refusals, and observable
results. Runtime roles, tool syntax, context limits, configuration keys, and paths
are adapters. Replace a binding while holding the kernel fixed: if its decisions
or result meanings change, the binding was structural and neutrality is unproven.
